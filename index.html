Case 01 · Spry Unified Billing Dashboard

One billing workspace that reconfigures itself for seven kinds of practice.

Spry sells software and services in different combinations. A practice might run everything in-house, or hand claims to Spry's RCM team, or buy nothing but eligibility verification. Instead of forking the product into seven builds, I designed a single system that changes shape based on what each practice actually owns.

P1

The sidebar is the bracket

The early instinct is to grey out features a practice hasn't bought. I argued the opposite: if it isn't in your configuration, it doesn't exist in your nav.

No empty states, no "upgrade to unlock." Your sidebar is your product, so you never feel like you're missing something.

P2

Design for the most complex configuration first, then scale down

B-full has everything; simpler brackets remove elements rather than adding their own one-offs. The system degrades gracefully; it never forks into seven codebases that drift apart.

P3

Ownership drives interaction

When Spry's service team handles claims or verification, the biller still sees status everywhere, but only sees action buttons for the work they actually own. The rest reads "handled by Spry." Same table, different agency.

P4

Task queue, not dashboard

The landing answers "what do I need to do right now?", not "how is my practice performing?" The work is the landing. No overview page to click through, no charts competing for the top of the screen.

P5

One spatial model everywhere

Click a row, a detail panel opens on the right. Never a modal, never a new page, regardless of bracket. A single consistent gesture across the whole system means there's only one thing to learn.

A real iteration moment: I'd given Claude reference screenshots and it copied them literally. I pushed back: reference is direction, not a template. Each bracket should look native to its own user, not like a pasted screen.

P1

Equal columns hide the priority

Three side-by-side lists read as "three separate things," all equally urgent. I collapsed the hero heading and duplicate stat tiles, and rebuilt the page so visual weight maps to what actually needs attention first.

P2

Prior auth and eligibility are two halves of one job

So they live inside a single Verification Tickets container with a shared count strip, not two unrelated cards. The frame is what tells you they belong together. Communications got demoted to a split panel that surfaces only what needs a reply.

P3

Make the work legible at a glance

Counts and dates on every applicable element, age indicators on each ticket row, and "View all" as a real bordered button, not a faint text link. No vague prompts; every tile points at an action.

Priority at equal urgency

If 50 messages all carry "Urgent," showing three of them is arbitrary. What's the real ranking logic?

Pre-attentive hierarchy

A coordinator should detect what matters before reading. Sections still read at too-similar weights.

Space utilization

Repeated padding and redundant headers waste vertical room that could carry more usable signal.

Stress test written into the brief: the layout must hold at 50+ urgent messages and 200+ tickets, not just the happy-path demo state.

How I work

A few things that hold true across projects, pulled from how I actually design, not a mission statement.

01

Additive, not destructive

I layer onto flows people already know rather than replacing them. New capability should feel like it was always there, not like a relearn.

02

Prototype to find the truth

Static mockups hide the hard states. I build clickable React so failures, partial states, and edge cases show up before they reach a developer.

03

Progressive disclosure

Drawers, hover cards, collapsible panels. Show the decision-level information first; let depth open on demand instead of crowding the surface.

04

Design the data, not just the screen

In billing the UI is only as honest as the payload. I read the SQL and inspect the API so the interface tells the truth.

05

Systems over screens

One spatial model, one set of patterns, configured for many cases. Consistency is what makes a complex product learnable.

06

Name the unsolved part

Shipping isn't the end of thinking. I write down what's still hard and the stress conditions it has to survive, so the next iteration starts honest.
